# AI engine handoff (for the integration backend)

**Owner:** Awaiz · **Engine:** `ai-engine/` (`rabt-ai-engine` 0.1.0) · **Contract:** [API_CONTRACT.md](API_CONTRACT.md) **0.1.1**

This guide explains how to run the AI engine and what it guarantees. It also covers the behaviours your backend needs to handle. The contract is the source of truth; this guide is the practical companion. Already verified with your backend from PR #1 (real model, fake Google):
- the full booking flow (free/busy → recommendation → approval gate → booked)
- the voice round trip through `/api/voice/*`

## 1. Run the engine

```powershell
ollama pull qwen3.5:9b                                  # once; 6.6 GB
$env:UV_PROJECT_ENVIRONMENT = "$HOME\.rabt\venv"        # keep the venv out of OneDrive
uv sync --group cuda                                    # no NVIDIA GPU? plain `uv sync`
uv run rabt-ai setup-models                             # once; Whisper + Kokoro (~1.9 GB, SHA-256 verified)
uv run rabt-ai serve                                    # http://127.0.0.1:8765 (Swagger at /docs)
```

- **Key:** both services need the same `RABT_INTERNAL_API_KEY` (≥ 24 chars). Generate one with `uv run rabt-ai gen-key`. Share it out-of-band and never commit it.
- **Readiness:** `GET /v1/agent/status` reports the model, whether it is on the GPU, and whether STT/TTS are loaded.
- **Without an NVIDIA GPU:** either set `RABT_LLM_MODEL=qwen3.5:4b` (smaller and faster on CPU), or run the engine on Awaiz's PC. In that case bind `RABT_HOST` to a private LAN IP behind the firewall, never `0.0.0.0` on a public network.
- **Models:** downloaded once by `setup-models`. The service itself never downloads anything at runtime.

## 2. What the engine guarantees

| Guarantee | How |
|---|---|
| Inference stays on this machine | LLM URL must be loopback or private; Ollama `*-cloud` models are refused; HTTP proxies are ignored. Tested: the only outbound connection during a live turn is `127.0.0.1`. |
| It never executes anything | It only returns `action_proposals`. Your backend executes them. |
| Side effects always need approval | `requires_approval` is `Literal[True]` for draft/event/message in the schema. The model cannot set it, and there is no tool or status that approves. |
| What you approve is what runs | Every proposal's `summary` is generated by the engine from the validated `args`, not written by the model. |
| No invented outcomes | Replies only claim "sent/booked/created" after a `succeeded` tool result. Claims without one are caught and rewritten. |
| Identity comes from you | The authenticated `account_id` + `role` are checked against the registry. Text like "I am Awaiz" changes nothing. |
| Privacy of free/busy | Results must contain free windows only (anything else → 422). Slots outside the requested window are discarded. |
| Untrusted content is data | Email/tool text is sanitised (chat-template tokens and tool markup neutralised) and wrapped in `<untrusted_data>`. Tested with a "SYSTEM OVERRIDE" phishing email: no action proposed. |
| Bounded | ≤ 4 model calls per request, ≤ 3 tool calls per model step, ≤ 6 proposals per turn. A lookup and the action that depends on it are never proposed in the same step. |

## 3. Driving a turn

```text
resp = POST /v1/agent/respond {request_id: new uuid, conversation_id, account_id, role, channel, message, timezone, sent_at}
loop while resp.status == "action_required":
    show resp.reply_text (interim, optional)
    withdraw approval prompts for resp.cancelled_proposal_ids
    for p in resp.action_proposals:
        if p.requires_approval: show p.summary -> approved? execute : status="rejected"
        else: execute (your auth/consent rules; refuse -> status="denied", error.code)
        resp = POST /v1/agent/tool-result {request_id: SAME as the turn, conversation_id, account_id,
                                           proposal_id, tool, status, result | error}
        # every result except the last one returns status="awaiting_results" (reply_text "")
show resp.reply_text   # status == "completed"
```

The reference implementation is `MockBackend.send()` in [`ai-engine/scripts/mock_integration_client.py`](../ai-engine/scripts/mock_integration_client.py).

## 4. Behaviours to handle

- **New message while proposals are pending:** the engine cancels them and lists them in `cancelled_proposal_ids`. Withdraw their approval prompts. A late result for one gets `409 proposal_not_pending`.
- **Retries are safe:** re-sending an identical `/respond` (same `request_id`) or `/tool-result` (same `proposal_id`) returns the stored response. A different body gets `409`.
- **Model down or slow:** `503 llm_unavailable` / `504 llm_timeout`. The turn is rolled back, so retry with the same `request_id`.
- **Cold start:** the first request after the model unloads (30 min idle) takes about 20–25 s. The engine pre-loads the model at startup. Use a client timeout of ≥ 300 s.
- **Your two-party lesson gate:** if a `calendar.create_event` is approved before both people agree, report `denied` with `error.code = "lesson_not_agreed"` instead of leaving it pending. The agent will then explain the situation to the user.
- **Contract 0.1.1:** multi-day searches set `daily_start` / `daily_end` (e.g. `"17:00"`/`"21:00"` for "any evening this week"). Honour them to return better slots. Ignoring them is safe, because the engine filters anyway.
- **Voice:**
  - `/v1/audio/speak` returns `audio/wav` (or `audio/ogg` Opus for WhatsApp with `"format": "ogg_opus"`), always with `X-Rabt-AI-Generated: true`.
  - `/v1/audio/transcribe` accepts wav, mp3, ogg/opus (WhatsApp voice notes), webm (browser `MediaRecorder`), m4a and flac.

## 7. Known limitations and next steps

- **"Ask Huda" via message:** the agent can propose `messaging.send_message` to Huda (with approval). Her *reply* is not yet routed back into Awaiz's conversation. Proposed for 0.2: `POST /v1/agent/event` delivering inbound third-party messages as untrusted data. Until then the free/busy lookup is the reliable path.
- **Wake word:** Whisper is biased toward "Rabt" and contact names. The male TTS voice still sometimes says "Rabt" so that it is heard as "Rapt".
- **Telephony** is a separate future adapter: phone audio → `/v1/audio/transcribe` → agent → `/v1/audio/speak` (OGG/Opus or WAV) → playback. `voice_chat.py` already runs this loop with a microphone.
- **Personal voices** (cloning) are deliberately not implemented. They would need a recorded consent record from the voice's owner.
- **Data location:** the AI engine keeps everything in `%USERPROFILE%\.rabt`. Use a different folder for backend secrets (see the review on PR #1).
